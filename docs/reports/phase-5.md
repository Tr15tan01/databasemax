## Implemented

- **Host registry and health.**
  - `register-host` CLI: the token is taken from the environment or stdin, then verified live (the provisioner must report the same host name and region).
  - Per-host encrypted tokens and a bootstrap host from `PROVISIONER_URL`.
  - Heartbeats every minute; offline after 2 minutes; the host returns to its previous status when it answers again.
  - Drain, undrain and retire (retire only when empty; re-auth, reason and audit required).
- **Placement:**
  - capacity- and constraint-aware, serialized with row locks;
  - allocations counted from the control plane's own records, including moves in flight;
  - re-places after `capacity_exceeded` or an unreachable host, as long as nothing was created yet.
- **Per-host routing of every infrastructure call** (`ProvisionerPool`): jobs, metrics (now collected in parallel), reconciliation, backups (verification on the backup's host, expiry there, relays), and admin views.
- **Worker hosts** (`docker-compose.worker.yml`):
  - instance ports published on the private IP from a fixed per-instance range;
  - `pg_hba` allows the gateway's private address;
  - firewall rules generated by `app.cli firewall-plan`;
  - production refuses to publish until egress blocking is acknowledged;
  - host labels on containers, so several provisioners can safely share one Docker engine.
- **Moves between hosts:**
  - read-only and disconnect, consistent backup, restore on the target with the same role and password, switch, verify, then remove the old instance;
  - rollback before the switch; the job resumes after interruption;
  - the gateway returns "being moved" during a move; the customer is notified.
- **Cross-host backups:** encrypted objects are relayed between per-host local stores. Only ciphertext passes through the control plane, and the receiver verifies the SHA-256.
- **UI:**
  - Admin → Hosts: health, reserved vs budget, labels, drain/undrain/retire, how to add a host.
  - A **Move host** action on admin database pages.
  - Customer banners for "moving" and "server unavailable".
  - Status badges for moving, draining, offline and retired.
- **Noise reduction:** "instance missing" is reported at most once per database per hour, and the alert counts distinct databases.

`test_multi_host_lifecycle` runs these steps in order:
1. Drain host 1; the new database lands on host 2 and is reachable through the gateway via a published port.
2. Back up on host 2; clone to host 1 through an encrypted relay; the temporary replica is removed.
3. Move host 2 → host 1: same URL and password, rows written before the move are present, the old instance is gone.
4. Kill host 2: it goes offline with an alert, its database is marked unavailable and refused at the gateway, nothing is reassigned, and new databases go to host 1.

- An E2E locator matched several "Delete" buttons.
- An E2E wait depended on the backups page's 30-second refresh.

## Security checks

- **Per-host provisioner tokens:** encrypted at rest and never passed in argv. Registration fails unless the provisioner proves it holds the token and reports the expected name and region.
- **Worker exposure:** bound to private IPs, with firewall plan and production guard (threat model T8a).
- **Customer roles on worker instances** accept connections only from the gateway's address.
- **Cross-host relays** carry ciphertext only; every host needs the same backup keys.
- **Admin host actions and moves** require recent re-authentication and a reason, and are audited. The customer is notified of moves.

## Known limitations

1. **Not yet run on real VMs.** Both "hosts" ran on one machine. On real VMs, the published-port, NSG/firewall and gateway-to-worker path still need checking (`docs/deployment/oci.md` §11).
2. **Gateway-to-worker traffic is plaintext** on the VCN; internal TLS is still open.
3. **Downtime during a move:** writes are blocked for the whole backup and restore time. There is no live migration, replication or automatic failover.
4. **Local-only backups share their host's failure domain.** If a worker VM is lost, its local backups are gone too; use the S3/OCI store in production.
5. **The gateway is still a single instance** on the main VM, which is a single point of failure.
