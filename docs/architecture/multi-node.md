# Multi-node data plane (Phase 5)

Status: **implemented and tested** with two provisioners on one machine
(`apps/api/tests/test_multihost_integration.py`). It has not yet run across two real OCI VMs;
see the checklist in `docs/deployment/oci.md` §11.

## Topology

```
                  internet :443 / :5432
                          │
   ┌──────────── main VM (control plane) ────────────┐
   │ Caddy · web · API · worker · control DB · Redis │
   │ TLS gateway ── loopback ──► local instances     │
   │ provisioner (bootstrap host) + host agent       │
   └───────┬──────────────────────────────┬──────────┘
           │ VCN private network          │
   provisioner API :8090           instance ports :20000-29999
   (from control plane only)       (from the gateway only)
           │                              │
   ┌───────▼────── worker VM (host-setup.sh --role worker) ───┐
   │ provisioner + host agent + customer instances            │
   └───────────────────────────────────────────────────────────┘
```

- **One public entry point.** Customers keep connecting to `db-<id>.<domain>:5432` on the
  gateway, whichever host runs their database. The gateway resolves each route to
  `internal_endpoint_host:port`:
  - `127.0.0.1:<port>` for instances on the main VM;
  - `<worker private IP>:<port>` for instances on worker hosts.
- **Worker hosts listen for instances only on their private address** (plus loopback), from a fixed range
  that is recorded per instance, so ports are stable across restarts. PostgreSQL on those
  instances accepts customer roles only from the gateway's private address
  (`DMX_EXTRA_CLIENT_CIDRS`). The worker firewall is generated by `app.cli firewall-plan`.
  It allows the provisioner port only from the control plane and the instance ports only from
  the gateway, and drops new outbound connections from the published network. Production
  provisioners refuse to start with `DMX_PUBLISH_IP` set until `DMX_PUBLISH_EGRESS_BLOCKED=true`.
- Gateway → worker traffic crosses the VCN in plaintext. Internal TLS is an open item in
  `docs/security/review-2026-09.md`.

## Host registry

`infrastructure_hosts`:
- name, region, endpoint and status (`active | draining | offline | retired`);
- labels, the last capacity report and heartbeat, and the last error;
- the provisioner token, **encrypted** in `secrets`.

The bootstrap provisioner (`PROVISIONER_URL`) registers itself on first contact and uses the
environment token. Every other host is registered from the operator CLI:

```
DMX_HOST_TOKEN=… python -m app.cli register-host --name worker-2 --endpoint http://10.0.1.12:8090 --region <r>
```

The token is read from the environment or stdin, never from argv. The CLI calls the provisioner
with the token and checks that the reported host name and region match before storing anything.

## Health and failure detection

- The worker heartbeats every non-retired host each minute (`capacity`).
- If a host has not answered for **2 minutes**, it goes `offline`. This is audited
  (`infrastructure.host_offline`) and raises a critical alert that says how many databases are
  affected.
- An offline host is excluded from placement and from metrics collection.
- The gateway answers its databases' clients with *"the server hosting this database is
  unavailable"*, and the dashboard shows a banner (`host_status = unavailable`).
- **Nothing is re-created or moved elsewhere.** The data is on that host's volumes. When the
  host answers again it returns to its previous status (`active` or `draining`).

## Placement

`app/provisioning/placement.py`, called by the create/clone job before anything is created:

- **Eligible host:** `active`, same region, fresh heartbeat, carries every required label, and
  the instance still fits the host's reported budgets (memory, disk, instance count).
- **Allocations** come from the control plane's own records (every non-deleted database placed
  on the host, plus moves in flight), so back-to-back creates don't overcommit.
- **Host rows are locked** while choosing.
- **Among eligible hosts,** the one with the largest minimum free fraction (memory / disk /
  CPU) after placement wins. This spreads load and limits the blast radius.
- **The provisioner stays authoritative.** On `capacity_exceeded`, or if the host is
  unreachable before anything was created, the job excludes that host and places again.
- **Once an instance exists, the host is fixed.**

## Moves between hosts (operator-initiated)

`POST /admin/databases/{id}/move` (recent re-auth, reason, audited, owner notified) starts the
`migrate` job:

1. Set the source to `default_transaction_read_only` and terminate the role's sessions. The
   gateway already refuses new connections, because the status is `migrating`.
2. Take a consistent `migration` backup.
3. Create an instance on the target host and configure it with the **same role and password**
   (from the stored credential; the target only sees a SCRAM verifier).
4. Restore. If the backup is in the source host's local store, the encrypted object is first
   relayed to the target and removed from it afterwards.
5. Switch `host_id`, instance and endpoint, then verify through the gateway, then `ready`.
6. Destroy the old instance. If that fails, the reconciler removes it later as "database lives
   on another host".

The URL and credentials don't change. Downtime is the backup and restore time; writes are
blocked from step 1. Before the switch, any failure rolls back: the source gets write access
again, the target instance is destroyed and the database returns to `ready`. Progress markers
in the job payload make retries resume rather than repeat.

## Backups across hosts

Each backup records the host whose store holds it:
- **Verification** runs on that host.
- **Expiry** deletes the object there.
- **Restores and clones** onto another host relay the object first, whenever the store is
  per-host (`local`).
- With a shared S3/OCI store no relay is needed.

Only ciphertext passes through the control plane (`GET`/`PUT /v1/backups/{db}/{backup}/object`).
Keys exist only on the provisioners, so **every host must have the same `DMX_BACKUP_KEYS`**.

## What is not claimed

- **Automatic failover:** there is no replication or promotion.
- **Automatic rebalancing:** moves are explicit.
- **Live migration without downtime.**
- **Cross-region placement:** each database stays in its region.
