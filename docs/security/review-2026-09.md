# Security review — September 2026 (Phases 3–4 code)

**Scope:** backups (crypto format, stores, dump/restore execution, verification), the root storage
agent and hard storage limits, backup/clone APIs and jobs, admin backup and security endpoints,
API rate limiting and gateway connection management. Earlier Phase 1–2 surfaces were
skimmed for critical issues.

**Method:**
- An independent review pass by a separate agent that had not written the code (read-only,
  file-and-line findings).
- The author then reproduced each finding, fixed it and added regression tests.

This is **not** an external penetration test, which is still an open item before launch.

**Status legend:** ✅ fixed and tested · 🟡 mitigated or partly fixed · ⚪ accepted risk, with the reason given.

## Findings and remediation

| ID | Sev. | Finding | Status | Fix and evidence |
|---|---|---|---|---|
| H1 | **High** | **Privilege escalation during restore.** `pg_restore` ran as the instance superuser with `--role=<customer>`. Customer SQL that runs during COPY (CHECK constraints, defaults, domain checks) could `RESET ROLE` and `ALTER ROLE … SUPERUSER`. **Reproduced**: the customer role became superuser on the clone. | ✅ | Restores now log in as a throwaway `dmx_r_*` role. It is `NOSUPERUSER`, a member of the customer role only, `VALID UNTIL` +6 h, and allowed only over the local socket (`local all +dmx_restorers scram-sha-256`; `host … reject`). The role is dropped (`REASSIGN OWNED`/`DROP OWNED`) afterwards. The same applies to scratch verification instances. Test: `apps/provisioner/tests/test_restore_privilege.py` runs the exploit and asserts that no customer role is superuser, the malicious restore still succeeds harmlessly, `COPY … TO PROGRAM` is denied, and no restore role is left behind. |
| H2 | High | **`pg_dump` could hang forever holding the instance lock.** A tenant holding an `ACCESS EXCLUSIVE` lock blocks the dump. That blocks stop/delete/suspend, and each such tenant pins a provisioner thread. | ✅ | `--lock-wait-timeout=60s`. Dump and restore are wrapped in coreutils `timeout --kill-after=30 <DMX_BACKUP_TIMEOUT_SECONDS>` inside the instance. Backups no longer take the instance lock, so a stop or delete wins and the backup fails and retries. |
| M1 | Medium | **Admin suspension could be escaped by cloning** a backup of a suspended database. | ✅ | Clones and restores are refused (409 `suspended`) and audited as `database.clone_refused`. Test: `test_suspended_database_cannot_be_cloned`. |
| M2 | Medium | **Shared backup storage could be exhausted by one tenant.** Repeated copy-and-delete cycles filled it, the budget check ignored the size of the dump about to be written, and concurrent dumps overshot it. | ✅ | Per-account allowance for on-demand, pre-copy and final backups (plan `user_backup_storage_mb`, 2× total storage; migration 0004). Before a dump, the provisioner reserves the database's size against the budget and requires free disk of estimate + 512 MB. Users can delete backups (`DELETE /backups/{id}`, re-auth, audited). Production guidance is off-host storage (S3/OCI), and local backups belong on a separate filesystem (`docs/deployment/oci.md`). Test: `test_user_backup_allowance_and_delete`. |
| M3 | Medium | **Disk accounting ignored volume growth.** Capacity used creation-time labels, and resize had no capacity check. | ✅ | Capacity now sums the storage agent's real image sizes, including orphaned images. `resize_storage` checks the budget before growing. |
| L1 | Low | **Backup objects weren't bound to their identity, and were read twice** (verify pass, then a second open for restore). | ✅ | New format `DMXB2`: the `<database id>/<backup id>` context is authenticated in every chunk's AAD (`DMXB1` is still readable). The object is opened once: authenticated plus SHA-256, then the same file handle is rewound for restore. Remote objects are spooled as ciphertext. Tests: `test_context_binding`, `test_legacy_format_still_readable`. |
| L2 | Low | **Retrying a failed clone could produce an empty database marked "restored".** | ✅ | `data_restored_at` is reset in final-failure cleanup. Test: `test_failed_clone_resets_restore_marker`. |
| L3 | Low | **Gateway per-IP limits were bypassable across an IPv6 /64, and table overflow reset everyone's windows.** | ✅ | Limits are keyed per IPv4 address or per IPv6 /64 (IPv4-mapped addresses are normalised). Eviction drops only idle entries. Tests: `test_client_key_groups_ipv6_by_64`, `test_rate_table_eviction_keeps_active_clients`. |
| L4 | Low | **Verification false positives.** The table count was taken outside the dump's snapshot, and the scratch instance was always 1 GB. | ✅ | The table count and `pg_dump --snapshot` use the same exported REPEATABLE READ snapshot. Scratch instances are sized from the source's allocation. |
| L5 | Low | **Encrypted objects could outlive retention.** Failed or swept backups weren't purged, and agent images could be orphaned. | ✅ | The expiry task purges objects of failed backups after 1 h, and objects of user-deleted backups. The reconciler calls `POST /v1/maintenance/orphan-volumes` (agent images without an instance, older than 1 h; stale verify instances). |
| I1 | Info | No check that the instance belongs to the database named in backup requests. | ✅ | `create_backup` verifies the instance's `io.databasemax.database` label (`test_backup_refuses_mismatched_database_id`). |
| I2 | Info | Negative `Content-Length` could hang a storage-agent thread. | ✅ | Rejected with 400. |
| I3 | Info | The soft storage limit (`default_transaction_read_only`) can be overridden per session. Shrinking an allocation keeps the larger filesystem. | ⚪ | Accepted. The hard limit is the security boundary, and it bounds overage to the filesystem size (allocation + 64 MB + 5 %, or a previously paid-for larger allocation). Usage above the allocation is measured and shown. |
| I4 | Info | Non-production environments silently use the built-in development backup key. | 🟡 | A startup warning is logged. Production refuses to start without a non-dev key. Runbook: staging with real data must set `DMX_BACKUP_KEYS`. |
| I5 | Info | Admin "verify now" and "back up now" didn't require recent re-authentication. | ✅ | `require_recent_auth` added. |

## Also changed as part of this review cycle

- **Hard storage limits** now put the customer database in its own tablespace on its own
  filesystem, separate from PGDATA and WAL. While testing the limits, a full data filesystem
  made the checkpointer PANIC (`pg_logical/replorigin_checkpoint.tmp: No space left`). With
  the tablespace split, a full database only produces `could not extend file` errors. Regression:
  `test_hard_quota_integration.py` also checks that `CREATE TABLE … TABLESPACE pg_default` is
  denied.
- **Per-credential API budgets:** per API key, per user and per write, plus limits on
  credential reveals and API-key creation (`tests/test_rate_limits.py`).
- **Gateway:** per-client concurrency cap and TCP keepalive. **PostgreSQL:**
  `idle_in_transaction_session_timeout=30min` and keepalives.
- **Security monitoring:** Admin → Security shows failed-login and targeted-account signals,
  credential reveals, sensitive actions and alerts (`app/monitoring/security.py`).
