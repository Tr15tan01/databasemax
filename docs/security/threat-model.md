# DatabaseMax — Threat Model (Phase 1)

Method: STRIDE-style review of each trust boundary in `docs/architecture/overview.md`.
Status legend: **Implemented** (code exists and has tests) · **Partial** · **Planned** (phase noted).
An internal independent review of the Phase 3–4 code, with a tracked remediation list, is in
`docs/security/review-2026-09.md`. An external penetration test is still open.

| # | Threat | Mitigations | Status |
|---|---|---|---|
| T1 | **Account takeover** (credential stuffing, brute force, session theft) | Argon2id (m=64 MiB, t=3, p=4); generic login errors; per-IP and per-account progressive throttling in Redis; session tokens are 256-bit random, stored as SHA-256 hashes, HttpOnly/Secure/SameSite=Lax cookies; session list + revocation; password change/reset revokes other sessions; security-sensitive login notification | Implemented |
| T2 | **Cross-tenant access** (IDOR, forgotten filters) | Owner-scoped repository queries; 404 on foreign ids; Postgres RLS forced on tenant tables as a second layer; API-key project allowlists; cross-tenant tests | Implemented |
| T3 | **Database credential leakage** | SCRAM verifiers sent to PG (no plaintext in PG/provisioner); AES-GCM encrypted at rest with keyed AAD; reveal is explicit + audited; log redaction filter; admin UI never shows passwords; rotation invalidates old password and kills sessions | Implemented |
| T4 | **SQL injection** | SQLAlchemy parameterized queries; identifiers in customer PG built with `psycopg.sql.Identifier`/`Literal` after regex validation | Implemented |
| T5 | **SSRF** | The backend makes outbound requests only to fixed hosts (Google OAuth endpoints, Paddle API, provisioner, SMTP) configured by operators; no user-supplied URLs are fetched; OAuth redirect URIs are fixed from configuration | Implemented |
| T6 | **Instance escape / cross-tenant access on the host** | Customers run only SQL as a non-superuser role (no untrusted languages, no `COPY PROGRAM`, no `pg_read_server_files`). Each database is a separate PostgreSQL server under its **own system user** (files 0700, signals and ptrace across instances impossible), in a systemd sandbox: empty capability set, `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, `ProtectProc=invisible`, `ProtectKernel*`, `RestrictNamespaces`, `MemoryDenyWriteExecute` (JIT off), `@system-service` syscall filter, a private view of `/var/lib/databasemax` containing only its own filesystems, `/etc/databasemax` and the code tree inaccessible, `IPAddressDeny=any` except loopback; cgroup CPU/memory/task limits; kernel patching via unattended-upgrades | Implemented (unlike containers there is no separate mount/PID namespace per filesystem root; AppArmor profile: Phase 4) |
| T7 | **Privilege escalation** (customer → superuser, user → admin) | Customer role is `NOSUPERUSER NOCREATEROLE NOREPLICATION NOBYPASSRLS`; `dmx_admin` (and every `dmx_*`/`pg_*` name) rejected at the gateway, and pg_hba allows `dmx_admin` only from 127.0.0.1 with a per-instance HMAC-derived password; admin role only via audited CLI assignment table; admin endpoints check role server-side + recent re-authentication for sensitive actions | Implemented |
| T8a | **Worker-host exposure (multi-node)** | Provisioner and instance ports bound to the VCN private address only; firewall plan (`dmx-admin firewall-plan`) allows them only from the control-plane / gateway VM; instances can't open outbound connections (`IPAddressDeny=any`); per-host provisioner tokens stored encrypted; customer roles accepted only from the gateway's private address; cross-host backup relay moves ciphertext only | Implemented; not yet exercised on real OCI VMs |
| T8 | **Network exposure** | Only 80/443/5432 public (plus SSH restricted by OCI NSG to admin IPs); everything else binds to loopback (API, internal API, web, provisioner, gateway status, Redis, customer databases) or a unix socket (control DB, host agent); `DMX-INPUT` firewall chain and rules in `docs/deployment/oci.md` | Implemented (config) / verification script provided |
| T9 | **Malicious provisioning requests** | Pydantic validation; allowlisted versions/profiles; users cannot supply binaries, paths, mounts, networks, capabilities, env or server settings; the provisioner re-validates everything and the root host agent validates again and renders all files itself from bounded values | Implemented |
| T10 | **Resource exhaustion** | Plan quotas checked transactionally; per-user concurrent job cap; per-instance CPU/memory/PID limits; data-plane capacity budget; hard per-instance storage limits (fixed-size data + WAL filesystems, root host agent with a closed API on a unix socket); all customer databases together capped by `dmx-customers.slice`; gateway connection caps and handshake timeouts; request size limit (1 MiB) and rate limits on API | Implemented |
| T11 | **Billing manipulation** | Entitlements change only from verified Paddle webhooks or reconciliation (never from the checkout success page); plan ids mapped server-side; webhooks idempotent by event id | Implemented (not tested against live Paddle — needs sandbox credentials) |
| T12 | **Webhook forgery / replay** | `Paddle-Signature` HMAC-SHA256 over `ts:body`, constant-time compare, 5-minute timestamp tolerance, event-id dedupe | Implemented |
| T13 | **Backup compromise / tampering / restore-time escalation** | Restores run as a throwaway non-superuser role (review H1); chunked AES-256-GCM with keys only on the provisioner (not API/worker/web); per-chunk authentication with counter + final flag (tamper/reorder/truncation rejected) and SHA-256 recorded in the control plane, both checked before any restore; object keys derived from validated UUIDs (no client paths); files 0600 in a 0700 directory or a private bucket; restores only into new databases; scratch verification instances have no gateway network; no customer-facing download endpoint | Implemented (off-host copies require `DMX_BACKUP_STORE=s3`; OCI endpoint not yet exercised) |
| T14 | **Admin account compromise** | Same auth as users + re-authentication window for sensitive actions; all admin actions audited with reason; admin role grants audited; no password visibility | Implemented; 2FA/WebAuthn for admins: Planned (Phase 4) |
| T15 | **Secret exposure through logs** | Structured JSON logs with a redaction filter (password/token/secret/authorization/cookie/connection-string patterns); request bodies are never logged; tests assert passwords never appear in captured logs | Implemented |
| T16 | **Dependency / supply chain** | Lockfiles (uv.lock, pnpm-lock.yaml); CI: pip-audit, pnpm audit, Bandit, Semgrep, Trivy image scan, CodeQL-ready workflow; base images pinned by tag (pin by digest in prod) | Implemented in CI config (runs on GitHub) |
| T17 | **CSRF / XSS / open redirect** | Double-submit CSRF token + Origin check for cookie-authenticated mutations; React escaping, no `dangerouslySetInnerHTML` with user data; strict CSP via Caddy; `next` redirect parameters restricted to relative paths | Implemented |
| T18 | **Automated callers (AI agents, scripts) destroying data** | Agent keys (machine identities) and opted-in keys cannot run destructive operations (delete database/project/backup, rotate password): after normal validation the request is stored as an approval and answered `202 pending_approval`; only a signed-in dashboard session with recent re-authentication can approve (no API key can, including full-access keys); approval executes through the same service functions (same checks, quotas, audit) and inside a savepoint so a failed run changes nothing; requests expire after 24 h, are deduplicated per resource and capped at 20 pending per key; keys see only their own requests; RLS on `approval_requests`; every step audited (`approval.requested/approved/rejected`) with the key id; disabling the safeguard on a standard key requires re-authentication and agent keys can't disable it | Implemented |
| T19 | **Dashboard SQL editor misuse** (stolen session, runaway queries, API exhaustion, accidental data loss) | The editor connects through the gateway (TLS) as the customer's own role — never `dmx_admin` — so it can do exactly what the customer's clients can; signed-in dashboard session only (API keys refused) plus recent password confirmation, like revealing the password; one running query per user and 10 per API (Redis slots with expiry), 30 queries/min per user; 15 s `statement_timeout` backed by a client-side deadline that cancels and then drops the connection (the query can't disable it); results streamed from libpq and capped at 1,000 rows / 3 MB / 10,000 characters per value; the gateway refuses any single server message over 8 MB on editor connections (`application_name=dmx-sql-editor`) so one huge row can't exhaust API memory; COPY to/from the client refused; read-only mode runs in `BEGIN READ ONLY` after a snapshot (can't be switched back) with `default_transaction_read_only` and is always rolled back; write mode asks to confirm DROP/TRUNCATE/ALTER/DELETE/UPDATE (typing the database name for DROP, TRUNCATE and unfiltered DELETE/UPDATE); EXPLAIN ANALYZE always runs read-only; SQL text and results are never logged or stored server-side (history is kept in the browser tab's sessionStorage); audit records statement types, row count, duration and SQLSTATE; results rendered as text (no HTML), CSV export neutralises spreadsheet formulas | Implemented |
| T20 | **Live monitor / insights leaking data or overloading the data plane** | Live metrics are counts and rates only (no query text, client addresses or rows), read by the provisioner with fixed SQL; one provisioner sample per database per 2 s shared by all viewers (Redis), 120 requests/min per user, polling stops while the browser tab is hidden; insights run fixed catalog queries (statistics and metadata, never table contents) as the customer's role through the same bounded editor path, 10/min per user; suggested fixes are returned as text and never executed by the platform | Implemented |

## Residual risks (tracked)

1. The host agent runs as root (it creates system users, loop devices, mounts and unit files).
   Mitigations: stdlib-only code, unix socket reachable only by the provisioner's group, a closed
   set of operations with every value validated, fixed argv, no shell, files rendered from
   bounded values, systemd sandboxing (`ProtectSystem=yes`, `NoNewPrivileges`, no network
   families except AF_UNIX/AF_NETLINK). It needs a writable `/etc` (users, units).
2. Internal traffic between gateway and customer PG is plaintext over loopback (or, on worker
   hosts, the private VCN network, firewalled to the gateway VM). Internal TLS is a Phase 4 item.
3. Control-plane services share one kernel and one machine with customer databases; isolation
   relies on users, cgroups and the systemd sandbox rather than containers or VMs. Put customer
   databases on worker VMs (multi-node) for stronger separation.
4. Single VM = single failure domain. No HA is claimed.
5. No external penetration test yet.
6. With `DMX_BACKUP_STORE=local`, backups share the VM's failure domain; production should use
   the S3-compatible store (OCI Object Storage) — see `docs/deployment/oci.md` §backups.
7. Backup keys are required to restore anything: losing `DMX_BACKUP_KEYS` makes all backups
   unrecoverable. Keep an offline copy (runbook).
8. The SQL editor's read-only mode and destructive-statement confirmation guard against
   accidents, not against the account owner: the role can write anyway, and statements hidden in
   `DO` blocks or functions aren't classified. Server-side the API holds the customer's password
   in memory for the duration of a query (it already decrypts it to reveal it).
9. Editor, schema and insights connections all come from the API's address, so they share the
   gateway's per-IP connection rate (60 per 10 s by default). Raise `DMX_GATEWAY_PER_IP_RATE` if
   many users run queries at once.
